## Why this candidate, and the (b) arbitrage
The repo has **no `src/` directory** — the Stripe call lives in `controllers/api.js`.
That rules out arbitrage (a) ("prefer a repo with `src/`") and puts us in case
(b): widen the matcher's default glob. See "APIdrift changes" below.

Candidates considered and not pursued (per the task envelope, documented here
rather than actually cloned/tested, since hackathon-starter satisfied all three
success criteria):
- `ChurchApps/Api` — TS/Jest, but Yarn Berry with a `preinstall` that refuses
  npm; the verifier hardcodes `npm test`, likely fatal to `npm ci`/install.
- `FaisalMisbah23/microservices` (`payments/` subpackage) — code in
  `src/routes/new.ts`, but its tests mock `stripe.charges.create` and assert
  the exact call shape, so migrating to `paymentIntents.create` would turn the
  suite red by design. That's the *correct* moat behavior (draft PR), but it
  can't satisfy "tests pass after fix", so it was not used as the primary proof.

## APIdrift changes made (this repo, branch `feature/US-1-preuve-repo-reel`)

### A. `node_modules` availability in the workspace — `src/pipeline.ts`
`makeWorkspace()` copies the target repo into a disposable workspace excluding
`node_modules` (and `.git`). The verifier then runs `npm test` in that
workspace. On a real repo with real dependencies this always failed before
this change. Fix: after `host.prepare()` (so it's never part of the baseline
commit), `linkNodeModules()` symlinks the *target clone's own* installed
`node_modules` into the workspace, and registers `node_modules` in
`.git/info/exclude` so `git add -A` / `git diff` never see it. No implicit
`npm install`, no new CLI flag, no config surface — link-only, best-effort
(silently skipped if the clone has no `node_modules`, e.g. the zero-dependency
fixture).

### A-bis. `.gitignore` was being silently dropped from the workspace copy — `src/pipeline.ts`
Found while validating A on this real repo: `makeWorkspace`'s original filter
was `!src.includes('/.git')`, which — being a plain substring test — also
matches `/.gitignore`, `/.github`, `/.gitattributes`, etc. Losing `.gitignore`
meant the LocalGitHost baseline commit (`git add -A`) tracked build/coverage
artifacts (`tmp/coverage/**`, generated by this repo's `c8`+mocha test run)
that were only ever meant to stay untracked. On this repo that inflated a
one-file diff into a >20MB `git diff`, which crashed with `ENOBUFS`
(`spawnSync`'s default 1MB buffer) before ever reaching the verifier. Fixed by
matching exact path segments (`.git`, `node_modules`) instead of a raw
substring. This is a correctness bug independent of hackathon-starter — any
target repo with a `.gitignore`-covered generated file on disk at clone time
would have hit it.

### B. Matcher glob widened — `src/matcher/index.ts`
`loadProject()` only scanned `src/**/*.{js,ts,jsx,tsx}`; hackathon-starter has
no `src/`. Per the imposed spec: one fixed glob, no CLI flag, no
`apidrift.json` field. Now scans `**/*.{js,ts,jsx,tsx}` from the repo root,
excluding `node_modules`, `dist`, `build`, `out`, `coverage`, `.next`,
`vendor`, `examples`, `*.d.ts`, `*.test.*`, `*.spec.*`, `test/**`, `tests/**`,
`__tests__/**`.

Risk checked: the codemod's matcher (`stripe-charges-to-intents.ts`) matches
any `<obj>.charges.create(...)`, not just `stripe.charges.create(...)`. On the
real run against hackathon-starter this produced exactly **one** match:
`controllers/api.js:488`. No false positives were observed anywhere else in
the repo (checked via the actual pipeline run's `matches` array, length 1).
A dedicated regression test (`tests/matcher.test.ts`) also exercises a
synthetic `node_modules`/`dist`/`test`/`__tests__` tree with decoy
`.charges.create(` calls in the excluded paths, plus one real call in
`controllers/`, and asserts exactly one match survives — and that the
`acme-payments` fixture (which now exposes `lib/stripe-mock.js` to the widened
glob) still matches exactly once, since that file only *defines* a
`charges.create` method, never *calls* one.

## Run against the real repo
```
npx tsx src/cli.ts run /tmp/us1-target/hackathon-starter --deterministic-only --out /tmp/us1-out
```
- **Match:** `controllers/api.js:488` — `stripe.charges.create(`
- **Patch:** `fix.patch` (this directory) — `controllers/api.js`, 3
  insertions / 2 deletions: `charges` → `paymentIntents`, `source` →
  `payment_method`, `confirm: true` added.
- **PR.md:** `PR.md` (this directory) — states "All checks passed", lists the
  changed file, embeds the diff.
- **Tests after fix:** `npm test` in the workspace — **328 passing, 0 failing**,
  exit code 0 (`post-fix-verify-output.txt`, full output). Same pass count as
  baseline: the fix neither broke nor (per the coverage gap above) exercised
  anything new.
- **draft:** `false` — a real (non-draft) PR body was produced, matching a
  passing suite.

Note on `PR.md`'s "Verification" section: it shows the last 12 lines of
`stdout+stderr` (`src/pr.ts`), and on this repo that window lands on an
*intentional* `console.error` from a passing WebAuthn error-path test
(`test/webauthn.test.js:170`), not on the "328 passing" summary line. The
status line above it ("All checks passed") is still correct — confirmed
independently against the raw `verify.output` and the process exit code — but
the excerpt itself is a legitimate pre-existing rough edge (unrelated to this
US's two authorized changes) worth a follow-up: order stdout after stderr, or
label the excerpt, so an unlucky trailing stderr line from a passing test
never reads like a failure. Not fixed here since it wasn't in the authorized
change list.

## What's still open / risks
- The demonstrated proof does not validate `postStripe`'s *runtime* behavior
  (no test covers it) — only that the migration doesn't regress the existing
  suite. Flagged above; not something APIdrift can currently manufacture
  without also writing new tests, which is out of scope (tests are read-only
  to the fixer).
- `PR.md`'s verification excerpt (last 12 lines of combined stdout+stderr) is
  legitimately confusing on repos with trailing stderr noise from otherwise
  passing tests; suggested as a small follow-up, not fixed in this US.
- The widened default glob (B) is a global behavior change for every future
  target repo, not just this one — by design, per the task's spec (no
  per-repo config surface). Broader real-world validation across more repos
  in `docs/backlog.md` would be good next-step evidence.
