## APIdrift changes made (this repo, branch `feature/US-1-preuve-repo-reel`)

### A. `node_modules` availability in the workspace — `src/pipeline.ts`
`makeWorkspace()` copies the target repo into a disposable workspace excluding
`node_modules` (and `.git`). The verifier then runs `npm test` in that
workspace. On a real repo with real dependencies this always failed before
this change. Fix: after `host.prepare()` (so it's never part of the baseline
commit), `linkNodeModules()` symlinks the *target clone's own* installed
`node_modules` into the workspace, and registers `node_modules` in
`.git/info/exclude` so `git add -A` / `git diff` never see it. No implicit
`npm install`, no new CLI flag, no config surface — link-only, best-effort
(silently skipped if the clone has no `node_modules`, e.g. the zero-dependency
fixture).

### A-bis. `.gitignore` was being silently dropped from the workspace copy — `src/pipeline.ts`
Found while validating A on this real repo: `makeWorkspace`'s original filter
was `!src.includes('/.git')`, which — being a plain substring test — also
matches `/.gitignore`, `/.github`, `/.gitattributes`, etc. Losing `.gitignore`
meant the LocalGitHost baseline commit (`git add -A`) tracked build/coverage
artifacts (`tmp/coverage/**`, generated by this repo's `c8`+mocha test run)
that were only ever meant to stay untracked. On this repo that inflated a
one-file diff into a >20MB `git diff`, which crashed with `ENOBUFS`
(`spawnSync`'s default 1MB buffer) before ever reaching the verifier. Fixed by
matching exact path segments (`.git`, `node_modules`) instead of a raw
substring. This is a correctness bug independent of hackathon-starter — any
target repo with a `.gitignore`-covered generated file on disk at clone time
would have hit it.

### B. Matcher glob widened — `src/matcher/index.ts`
`loadProject()` only scanned `src/**/*.{js,ts,jsx,tsx}`; hackathon-starter has
no `src/`. Per the imposed spec: one fixed glob, no CLI flag, no
`apidrift.json` field. Now scans `**/*.{js,ts,jsx,tsx}` from the repo root,
excluding `node_modules`, `dist`, `build`, `out`, `coverage`, `.next`,
`vendor`, `examples`, `*.d.ts`, `*.test.*`, `*.spec.*`, `test/**`, `tests/**`,
`__tests__/**`.

Risk checked: the codemod's matcher (`stripe-charges-to-intents.ts`) matches
any `<obj>.charges.create(...)`, not just `stripe.charges.create(...)`. On the
real run against hackathon-starter this produced exactly **one** match:
`controllers/api.js:488`. No false positives were observed anywhere else in
the repo (checked via the actual pipeline run's `matches` array, length 1).
A dedicated regression test (`tests/matcher.test.ts`) also exercises a
synthetic `node_modules`/`dist`/`test`/`__tests__` tree with decoy
`.charges.create(` calls in the excluded paths, plus one real call in
`controllers/`, and asserts exactly one match survives — and that the
`acme-payments` fixture (which now exposes `lib/stripe-mock.js` to the widened
glob) still matches exactly once, since that file only *defines* a
`charges.create` method, never *calls* one.

## US-4 update — hardening the codemod against Stripe's real schema
- **Question:** does `stripe.paymentIntents.create({ ..., confirm: true })`
  (US-1's output, no `return_url`) actually work for every payment method, or
  only appear to because no test exercises it?
- **Answer, sourced:** the Stripe OpenAPI spec (`stripe/openapi`, `spec3.json`,
  API version `2026-08-26.dahlia`, fetched 2026-08-30) only marks
  `amount`/`currency` as `required` for `POST /v1/payment_intents` — it does
  not model `return_url` as required. Stripe's own API reference
  (https://docs.stripe.com/api/payment_intents/create, fetched 2026-08-30)
  spells out the actual (conditional) rule under
  `automatic_payment_methods.allow_redirects`: with the default `"always"`,
  `return_url` "may be required to confirm this PaymentIntent"; with
  `"never"`, "this PaymentIntent will not accept redirect-based payment
  methods ... `return_url` will not be required to confirm". So the original
  suspicion was directionally right but imprecise: the call isn't *always*
  broken, it's conditionally broken depending on the resolved payment method.
- **Fix:** the codemod now also adds
  `automatic_payment_methods: { enabled: true, allow_redirects: 'never' }`,
  which — per the documented rule above — removes the conditional
  `return_url` requirement, matching the old Charges API's no-redirect
  semantics. This repo's `fix.patch`/`PR.md` above reflect the new output.
- **New test:** `tests/stripe-charges-to-intents.test.ts` runs the actual
  codemod, extracts the generated call's argument object via the AST (no
  `eval`), and validates it against a vendorized extract of the Stripe spec
  (`fixtures/stripe-spec/payment_intents_create.extract.json`) plus a mocked
  HTTP endpoint encoding the documented conditional rule — no network, no
  Stripe key. Verified to fail when `confirm`, `payment_method`, or
  `automatic_payment_methods` is stripped from the codemod's output (checked
  by temporarily sabotaging `apply()`, confirming red, then reverting).
- **`src/pr.ts` fix:** see the "Fixed by US-4" note above.
