# Phase-0 spike: dynamic diff resolver, Stripe only (2026-09-10)

Proof-of-feasibility for the Free-tier design decision recorded in this
session: **no embedded codemod library** — the Free engine computes the API
diff live, from the user's own resolved "before" version, and hands it to the
user's own AI (BYOT) to fix. This spike proves the mechanism works end to end,
on Stripe, before any of the production US (N1..N5) get written.

## What this proves

```
resolved "before"  ──(not exercised here, see caveat below)
        │
        ▼
live fetch: https://docs.stripe.com/changelog.md          (REAL network call, no fixture)
        │
        ▼
detectChanges() (src/detection/) → a dynamically-computed `Change`           (nothing hardcoded)
        │
        ▼
genericSymbolCodemod() (src/matcher/symbol.ts) → AST match, no hand-written fix
        │
        ▼
runAgent() (src/fixer/agent.ts) → REAL model call (claude-haiku-4-5-20251001)
        │
        ▼
verify() → the target repo's OWN, unmodified tests as the gate
```

The Change used is real and was live on docs.stripe.com at spike time:
**"Removes support for specifying payment method types in Payment Intents and
Setup Intents"**, release `2026-08-26.preview` — `payment_method_types` is no
longer accepted on `paymentIntents.create/update/confirm` /
`setupIntents.create/update`.

## Target

A disposable, purpose-built fixture (`fixture-target-repo/`), not a real OSS
repo — the spike's question was "is the diff clean enough for the AI", not
"can we find a real repo with this exact pattern" (that methodology is
`docs/proof/US-1`/`US-6`'s job, for a shipped change). The fixture:
- `src/checkout.js` — creates a PaymentIntent passing `payment_method_types`,
  correct code for an account on an older API version;
- `node_modules/stripe/` — a small, RUNNABLE, offline stub of the Stripe
  client (not the real npm package: no real network Stripe calls are
  possible without a real Stripe test key). Its `paymentIntents`/`setupIntents`
  methods reproduce the REAL 2026-08-26.preview behavior described in the
  changelog: passing `payment_method_types` throws, mirroring Stripe's actual
  400 `payment_method_types_no_longer_supported` error.

## Results

- **Baseline** (`baseline-test-output.txt`): 0 pass / 1 fail — the stub
  enforces the real new behavior, so the unfixed code is genuinely red, not a
  no-op assertion.
- **Fix** (`fix.patch`): a 1-line diff — the AI agent deleted exactly
  `payment_method_types: ['card']` and nothing else, on its own, from the
  live-fetched `migration.detail` (the changelog's verbatim "## Impact" prose)
  with no other guidance.
- **Post-fix** (`post-fix-verify-output.txt`): 1 pass / 0 fail.
- **PR body** (`PR.md`): generated by the real `buildPrBody()`, non-draft.
  Notably, it also correctly disclosed that APIdrift could not read this
  repo's installed Stripe SDK default API version (the stub has no real
  `apiVersion.js`) — the existing US-9 guard degraded correctly (disclosure,
  not a block, not a silent pass) with zero glue code written for this spike.
- **Cost**: exactly one live model call (Haiku 4.5, ≤6 iterations, 4096
  tokens/call budget — the other 4 auto-executable changes detected in this
  release matched zero call sites in the tiny fixture and never reached the
  LLM).

## Honest verdict

On this one sample: **the diff was clean enough**. Stripe's changelog "Impact"
prose named the exact parameter, the exact affected endpoints, and the exact
remedy — the model needed no inference beyond "delete this key". This is
**one data point, not a statistical claim** — Stripe's changelog entries vary
in shape and clarity, and this path only ever sees forme #1 (request-shaped)
changes; forme #2 (response-shaped) changes are excluded upstream, by design,
before they'd ever reach the fixer. I would not yet generalize this result to
every Breaking row Stripe publishes.

## A real gap found here, now fixed

The generic matcher (`src/matcher/symbol.ts`) did not recognize
`const Stripe = require('stripe'); const stripe = new Stripe(...)` — an
extremely common CommonJS construction shape — at spike time; only ESM
`import Stripe from 'stripe'` and the `require('stripe')(...)` direct
factory-call form were resolved. The fixture in this directory therefore uses
ESM. This is now **fixed** (same change as this proof record):
`isVendorConstructor` in `src/matcher/symbol.ts` also resolves `new X(...)`
where `X`'s declaration traces back to `require(vendorModule)`. See
`tests/matcher-symbol.test.ts` for the regression test, and the new
anti-silence warning (`PipelineResult.warning`, wired in `src/pipeline.ts` and
`src/cli.ts`) for the remaining, still-documented gap (destructured
`const { Stripe } = require('stripe')`) — a detected change with 0 matches now
WARNS explicitly rather than reading as silent "nothing to do" whenever the
repo does construct the vendor client somewhere.

## Caveat: what this spike deliberately did NOT exercise

- The version-range walk ("from my pin to latest") — this spike asked
  `detectChanges` for one specific, known release, matching the
  already-existing `--detect --release` shape. Walking a range is production
  work (US-N2), not part of the feasibility question.
- The pinned-API-version guard actually blocking — that's already proven
  separately by the existing US-7/US-9 test suites; this spike's fixture
  deliberately has no readable pin so the guard degrades to disclosure, to
  keep the spike isolated to the one open question it was asked to answer.
